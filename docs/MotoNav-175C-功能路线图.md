# MotoNav 1.75C 功能路线图

> 目标：把 `ESP32-S3-Touch-AMOLED-1.75C` 做成一套适合摩托车长期使用的导航设备。
>
> 核心策略：先通过 USB 烧录把硬件底座、通信协议、OTA 能力和安全兜底做好；之后尽量只更新应用固件，不再反复拆车或连接 USB。

## 1. 当前基线（以本节为准）

### 1.1 当前发布版本与发布位置

- Android App：已发布 `v8.3.44`（`versionCode 147`，GitHub Release：`motonav-v8.3.44`）；上一正式版为 `v8.3.43`（`versionCode 146`）。
- 1.75C 固件：已发布 `v7.12.9-nav.5`（GitHub Release：`motonav-v8.3.44`）；上一稳定版为 `v7.12.9-nav.4`。
- 正式发布仓库：`shuiyeshanchuan/MotoNav`；App 和圆屏 OTA 均从这个仓库的非草稿、非预发布 Release 获取文件。
- 1.75C 稳定 OTA 索引当前指向 `v7.12.9-nav.5`；OTA 只使用 `*_app_0x10000.bin`，`*_full_0x0.bin` 仅用于 USB 救援。
- 当前发布 APK 的包名为 `com.motonav.u2b4f81869feb4118bb152504f57650e3`，发布签名 SHA-1 为 `49:7D:D6:15:13:34:EA:38:CD:C1:0A:7C:EB:C2:57:42:FE:85:B8:5C`。

### 1.2 已实现

- 1.75C 独立构建目标 `175c`，466×466 AMOLED/QSPI 配置，`LCD_RESET = GPIO1`、`TP_RESET = GPIO2`。
- AXP2101 电源管理、32MB Flash、`app5M_fat24M_32MB` 分区与双 OTA 应用分区。
- BLE 加密配对、自动连接最近一次圆屏、自动重连、状态重发、设备能力/板型/固件版本/OTA 状态查询。
- 导航、巡航、地图、转向、车道、电子眼、红绿灯、天气、音乐控制、歌词、来电显示、亮度、旋转、轨迹记录与 GPX 导出等现有基础功能。
- BLE OTA 完整实现：板型和版本检查、OTA 电源条件检查、SHA-256、RSA-2048 签名、分块 ACK、备用 OTA 分区写入、重启后的版本确认，以及 USB 完整镜像救援。
- App 内“检查稳定版更新”：从 GitHub 下载、校验并通过 BLE 更新圆屏固件；已完成至少一次真实设备的成功升级闭环。
- OTA 后 App 会在圆屏重新连接时主动重新读取版本和能力信息；`v8.3.34` 起不再把“已连接”错误地当成仍在重启倒计时。
- 1.75C PWR 键软件菜单：按住约 2 秒出现 `POWER OFF / RESTART`，松开 PWR 后触控确认；点空白取消后会清除本次菜单状态，下一次独立长按仍在 2 秒弹出；持续按住约 6 秒仍交给 PMIC 强制断电。
- `v7.12.9-nav.2`：PWR 检查提前到主循环开头，对瞬间低电平做 80 毫秒释放消抖；关机菜单压住导航、来电、天气、音乐和路口提示的刷新，原页面的触摸动作不会误选菜单。地图数据晚于导航指令到达时，先短暂显示 `LOADING MAP`，2.5 秒后仍没有地图则显示转向箭头。
- App 内“关于 MotoNav”菜单：显示当前版本，检查 GitHub 最新正式版、下载 APK、核验包名/版本号/签名并打开 Android 系统安装确认（`v8.3.35`）。

## 2. 标记说明

- `[烧录]`：需要重新通过 USB 刷入完整镜像或应用镜像。
- `[OTA]`：OTA 基础设施完成后，原则上可以不连接 USB 更新。
- `[双方]`：Android App 和 ESP32 固件需要同时更新。现有 1.75C 已具备签名 BLE OTA；本阶段仅改应用层协议，可通过 App 自更新与圆屏 OTA 更新。Bootloader、分区或 OTA 信任根变更仍需 USB。
- `[验证]`：主要是测试、测量和确认，不一定需要改代码。
- `[暂缓]`：有价值，但不应阻塞核心导航功能。
- `[x]`：已实现；如条目中另有“待实机验证”，则不代表所有真实场景已验收。
- `[验证中]`：代码和构建已完成，正在等待指定实机场景回归。

### 路线图维护约定

1. 本文件是 MotoNav 1.75C 的功能状态与下一步工作的唯一参考；新功能、版本号和验证结果必须先更新到这里。
2. 只有真实设备按验收条件通过，才能把“待实机验证”改为“已验证”。构建成功、静态校验或模拟测试不能替代实车验证。
3. 每个 OTA Release 必须记录 App 版本、固件版本、升级路径与 USB 救援文件；涉及分区、Bootloader 或 OTA 信任根的改动仍归入 `[烧录]`。

- [x] `[烧录]` 新增独立 OTA 控制、数据和状态通道，避免与导航文本通道混用。
- [x] `[烧录]` 支持固件元信息：板型、固件版本、协议版本、文件大小、SHA256 和最低电量要求。
- [x] `[烧录]` 支持固定大小分块、偏移、序号、确认和同一会话内重发；跨断线续传暂不启用。

- [ ] `[双方]` 骑行统计：里程、时长、平均速度、最高速度、停车次数。
- [ ] `[双方]` 轨迹自动分段、自动命名和异常轨迹修复。

## 7. 建议的实际开发顺序

### 阶段 A：1.75C 稳定基线，必须 USB

1. 完成屏幕、触摸、旋转、PMU、电池、音频和 BLE 的实机测试。
2. 修复所有会导致死机、花屏、触摸失灵、无法重连和异常关机的问题。
3. 增加固件版本、板型、协议版本和设备能力查询。
4. 固定一版可靠的 1.75C 基线固件，保存完整镜像、应用镜像和 SHA256。

### 阶段 B：OTA 基础设施，必须 USB 一次

1. 先用 USB 刷入带 BLE OTA 能力的基础固件。
2. Android App 增加固件包读取、manifest 校验、分块传输和进度显示。
3. 实现升级中断、断电、错误包、错误板型和失败回滚测试。
4. OTA 成功后读取设备版本，确认新旧 App 协议兼容。
5. 发布第一版“可 OTA 升级”的稳定基线。

### 阶段 C：后续功能尽量 OTA

1. 先更新显示和交互，不改分区和 Bootloader。
2. 再更新导航算法、地图渲染、天气、音乐和提示策略。
3. 每个版本都保留回滚版本和 USB 救砖镜像。
4. 只有涉及 Bootloader、分区、OTA 机制或严重兼容变化时，才重新 USB 烧录。
