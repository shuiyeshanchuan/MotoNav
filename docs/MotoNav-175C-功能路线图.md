# MotoNav 1.75C 功能路线图

> 目标：把 `ESP32-S3-Touch-AMOLED-1.75C` 做成一套适合摩托车长期使用的导航设备。
>
> 核心策略：先通过 USB 烧录把硬件底座、通信协议、OTA 能力和安全兜底做好；之后尽量只更新应用固件，不再反复拆车或连接 USB。

## 1. 当前基线（以本节为准）

### 1.1 当前发布版本与发布位置

- Android App：已发布 `v8.3.47`（`versionCode 150`，GitHub Release：`motonav-v8.3.47`）；上一正式版为 `v8.3.46`（`versionCode 149`）。
- 1.75C 固件：稳定版为 `v7.12.9-nav.6`（GitHub Release：`motonav-v8.3.47`）；上一稳定版为 `v7.12.9-nav.5`。
- 正式发布仓库：`shuiyeshanchuan/MotoNav`；App 和圆屏 OTA 均从这个仓库的非草稿、非预发布 Release 获取文件。
- 1.75C 稳定 OTA 索引当前指向 `v7.12.9-nav.6`；OTA 只使用 `*_app_0x10000.bin`，`*_full_0x0.bin` 仅用于 USB 救援。
- 当前发布 APK 的包名为 `com.motonav.u2b4f81869feb4118bb152504f57650e3`，发布签名 SHA-1 为 `49:7D:D6:15:13:34:EA:38:CD:C1:0A:7C:EB:C2:57:42:FE:85:B8:5C`。

### 1.2 已实现

- 1.75C 独立构建目标 `175c`，466×466 AMOLED/QSPI 配置，`LCD_RESET = GPIO1`、`TP_RESET = GPIO2`。
- AXP2101 电源管理、32MB Flash、`app5M_fat24M_32MB` 分区与双 OTA 应用分区。
- BLE 加密配对、自动连接最近一次圆屏、自动重连、状态重发、设备能力/板型/固件版本/OTA 状态查询。
- 导航、巡航、地图、转向、车道、电子眼、红绿灯、天气、音乐控制、歌词、来电显示、亮度、旋转、轨迹记录与 GPX 导出等现有基础功能。
- BLE OTA 完整实现：板型和版本检查、OTA 电源条件检查、SHA-256、RSA-2048 签名、分块 ACK、备用 OTA 分区写入、重启后的版本确认，以及 USB 完整镜像救援。
- App 内“检查稳定版更新”：从 GitHub 下载、校验并通过 BLE 更新圆屏固件；已完成至少一次真实设备的成功升级闭环。
- OTA 后 App 会在圆屏重新连接时主动重新读取版本和能力信息；`v8.3.34` 起不再把“已连接”错误地当成仍在重启倒计时。
- 1.75C PWR 键软件菜单：按住约 2 秒出现 `POWER OFF / RESTART`，松开 PWR 后触控确认；点空白取消后会清除本次菜单状态，下一次独立长按仍在 2 秒弹出；持续按住约 6 秒仍交给 PMIC 强制断电。

## 2. 标记说明

- `[烧录]`：需要重新通过 USB 刷入完整镜像或应用镜像。
- `[OTA]`：OTA 基础设施完成后，原则上可以不连接 USB 更新。
- `[双方]`：Android App 和 ESP32 固件需要同时更新。现有 1.75C 已具备签名 BLE OTA；本阶段仅改应用层协议，可通过 App 自更新与圆屏 OTA 更新。Bootloader、分区或 OTA 信任根变更仍需 USB。
- `[验证]`：主要是测试、测量和确认，不一定需要改代码。
- `[暂缓]`：有价值，但不应阻塞核心导航功能。
- `[x]`：已实现；如条目中另有“待实机验证”，则不代表所有真实场景已验收。
- `[验证中]`：代码和构建已完成，正在等待指定实机场景回归。

### 路线图维护约定

1. 本文件是 MotoNav 1.75C 的功能状态与下一步工作的唯一参考；新功能、版本号和验证结果必须先更新到这里。
2. 只有真实设备按验收条件通过，才能把“待实机验证”改为“已验证”。构建成功、静态校验或模拟测试不能替代实车验证。
3. 每个 OTA Release 必须记录 App 版本、固件版本、升级路径与 USB 救援文件；涉及分区、Bootloader 或 OTA 信任根的改动仍归入 `[烧录]`。

## 3. 第一阶段：先完成必须烧录的底座

这一阶段的目标是：烧录一次后，设备具备稳定运行、可靠通信和安全 OTA 的基础。

### 3.1 1.75C 硬件适配与启动

- [x] `[烧录]` 使用 1.75C 专用 GPIO 配置。
- [x] `[烧录]` 使用 32MB Flash 和 32MB 分区表。
- [x] `[烧录]` 保留 `app0/app1/otadata`，为后续 OTA 留出双应用空间。
- [ ] `[烧录]` 验证冷启动、热重启、PWR 断电重启和 BOOT 强制下载模式。
- [ ] `[烧录]` 验证屏幕每次启动都能正常点亮，无花屏、横线、随机颜色或白屏。
- [ ] `[烧录]` 验证触摸坐标、触摸方向和旋转后的坐标变换。
- [ ] `[烧录]` 验证屏幕旋转保存后，断电重启仍能恢复。
- [ ] `[烧录]` 验证快速刷屏开关在 1.75C 上不会造成撕裂、卡死或花屏。
- [ ] `[烧录]` 验证 QSPI 40/60/80MHz 三档的稳定性，默认保守使用 40MHz。
- [x] `[烧录]` 增加设备能力信息，至少报告板型、固件版本、分区版本和协议版本。
- [x] `[烧录]` 增加启动自检结果，方便通过 BLE 或串口判断屏幕、触摸、PMU 和存储状态。

验收标准：连续冷启动和断电启动至少 30 次；屏幕和触摸无随机失败；旋转和 QSPI 设置不会让设备无法启动。

### 3.2 电源、电池和温度

- [ ] `[烧录]` 验证 AXP2101 初始化、电池电量读取、充电状态和外部供电状态。
- [ ] `[烧录]` 验证插 USB 供电时不会因为“无导航五分钟”误关机。
- [ ] `[烧录]` 验证拔掉外部电源后，空闲关机计时重新开始。
- [x] `[烧录]` 增加低电量分级状态：正常、低电量、极低电量和未知状态。
- [x] `[烧录]` 抽出 OTA 前置条件检查：外部供电或电量至少 40%，且 PMU 温度不高于 70°C；正式 OTA 接入时直接复用。
- [x] `[烧录]` 增加 AXP2101 温度、外部输入电压和电池读数异常诊断；实际过热保护阈值仍需实机验证。
- [ ] `[烧录]` 评估行驶中持续供电时的温升，避免屏幕高亮、音频和充电同时造成过热。
- [ ] `[烧录]` 验证深睡唤醒、PWR 重启和 BLE 断开后的资源释放。

### 4.5 摔车/碰撞疑似事件与紧急联系人（安全关键，方案阶段）

> **安全边界：** 这项功能只能做“疑似事故检测 + 用户确认 + 联系人通知”，不能承诺零误判、零漏判，也不能替代安全气囊、专业救援设备或人工报警。单个加速度阈值不能直接触发联系。没有完成真实安装、封闭道路和手机后台可靠性验证前，不开放自动通知。

#### 4.5.1 可行性与硬件边界

- 1.75C 硬件具备板载 QMI8658 六轴 IMU（3 轴加速度 + 3 轴陀螺仪）。官方资料、示例和原理图： [Waveshare 1.75C 文档](https://docs.waveshare.com/ESP32-S3-Touch-AMOLED-1.75C)、[QMI8658 示例](https://github.com/waveshareteam/ESP32-S3-Touch-AMOLED-1.75C/tree/main/examples/arduino/04_LVGL_QMI8658_ui)、[原理图](https://files.waveshare.com/wiki/ESP32-S3-Touch-AMOLED-1.75C/ESP32-S3-Touch-AMOLED-1.75C-schematic.pdf)。当前 MotoNav 固件只使用触摸和 PMU，尚未初始化或读取 QMI8658；本地 SensorLib 虽有驱动，仍需实测总线、地址、轴向、中断和采样稳定性。
- QMI8658 与触摸共用 I2C，总线为项目当前的 GPIO15（SDA）/GPIO14（SCL），原理图标注地址 `0x6B` 和独立中断网络。不能直接假设中断 GPIO、安装方向和采样率，必须先做硬件探测与串口采样。
- 标准 1.75C 没有独立蜂窝通信和 GNSS。圆屏可以采集运动候选事件并通过 BLE 交给手机，但自动联系联系人依赖手机的定位、网络或 SIM、短信/通知权限和后台服务；手机断电、无网、无 SIM、BLE 断链或进程被系统杀死时，圆屏不能独立完成通知。
- 1.75C 原理图还包含麦克风和 ES8311 音频链路，但当前 MotoNav 没有麦克风录音或事故声音分析代码。结论是**建议纳入，但只作为可选的辅助证据，不是事故检测的必需条件或主判据**：碰撞声可能被风噪、发动机、喇叭、音乐和导航播报淹没，屏幕松脱或麦克风朝向变化也会让声音证据失效。先验证采样率、增益、风噪和与导航语音/音乐播放的冲突，再决定是否启用。
- 圆屏测到的是车体/支架的运动，不等于骑手身体受伤。安装刚度、松脱、外壳共振、车型、路面和屏幕方向都会改变数据；若要判断骑手是否被甩出或受伤，需要额外的车体速度/轮速和可穿戴或独立碰撞传感器，属于 `[外部硬件/验证]`，无法仅靠 OTA 补齐。

#### 4.5.2 检测状态机与多源证据

- [ ] `[双方]` 建立 `DISABLED → SETUP → ARMED → CANDIDATE → CONFIRMING → ESCALATING → ACK/RECOVERED/CANCELLED` 状态机。只有用户明确开始骑行、IMU 自检通过、手机定位和 BLE 链路可用、联系人配置有效时才进入 `ARMED`；停车、运输、充电、维修和设备被拿起时退出监测。
- [ ] `[双方]` 以高采样率记录加速度模长、冲击/jerk、陀螺角速度、姿态变化、翻转/持续倾角和传感器饱和状态；保留短时环形缓冲（默认只在手机本地加密保存）供复盘，不默认上传原始运动数据。采样率和窗口由实测数据确定，不能先写死一个“摔车阈值”。
- [ ] `[双方]` 候选事件必须满足有时间顺序的多项证据：骑行前有可信速度或导航状态，随后出现冲击或急剧 jerk、明显角速度/姿态突变，再出现持续静止、异常倾角或速度骤降；手机 GPS 速度/轨迹和手机传感器只能作为辅助交叉证据，不能在手机未固定时与车体 IMU 等权。
- [ ] `[双方]` 将麦克风声音作为可选的辅助证据：只在 IMU 冲击时间窗内提取短时能量、宽带瞬态、削波和频谱变化等特征，与冲击/姿态事件做时间对齐；只上传脱敏特征或事件摘要，不保存或上传连续原始录音，不做语音识别。麦克风不可用、被音频播放占用、削波或权限/驱动失败时，标记为“无音频证据”并继续使用 IMU/GPS 路径，不能因此判定安全或事故；不能因单次巨响直接触发联系人通知。
- [ ] `[双方]` 坑洼、减速带、急刹、正常压弯、停车倒车、扶车、掉屏、放置、维修振动和洗车作为明确负样本；受保护的封闭场地摔车模拟作为正样本。任何单一阈值、单次 BLE 断开或单次 GPS 跳点都不得直接联系联系人。
- [ ] `[OTA]` 圆屏和手机同时显示“检测到疑似事故”，播放声音/震动并开始可配置确认倒计时（初始建议 15–30 秒，最终由数据和实测决定）。圆屏大按钮、手机前台通知和物理/触摸取消必须可用；手动 SOS 保持独立入口，不能与自动判定共用唯一触发路径。
- [ ] `[双方]` 倒计时无响应且证据达到门槛后才进入 `ESCALATING`；明确区分“候选事件”“已确认待发送”“手机已发送”“联系人已确认”“发送失败”，没有手机确认不得在圆屏上显示已发送。

#### 4.5.3 手机网关、联系人和通信

- [ ] `[Android]` 复用现有前台服务保持 BLE 和定位，但为事故监控单独定义会话、权限自检、传感器健康和电池状态；Android 12+ 后台启动和 Android 14 前台服务类型限制必须逐机验证。[前台服务类型说明](https://developer.android.com/about/versions/14/changes/fgs-types-required)、[后台启动限制](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)
- [ ] `[Android]` 允许用户配置 1–3 名紧急联系人、联系人顺序、是否允许短信/网络通知、确认倒计时和测试模式；默认只通知用户明确配置的联系人，不自动拨打 110/120。自动拨号需要 `CALL_PHONE` 等权限并受系统/厂商限制；短信需要 `SEND_SMS`、可用 SIM、默认订阅和运营商支持，[SmsManager](https://developer.android.com/reference/android/telephony/SmsManager) 失败时必须显示失败并重试，不能假报成功。
- [ ] `[双方]` BLE 事件帧使用已有加密配对，同时增加事件 ID、单调序号、时间戳、传感器摘要、ACK、重试、超时和重放保护；断链期间只缓存并标记延迟，重连后不能把过期事件伪装成实时报警。
- [ ] `[Android]` 通知内容使用“可能发生事故”措辞，包含最后可信经纬度、定位精度、时间、最后速度、圆屏电量、事件置信等级、取消倒计时和发送状态；不默认上传连续轨迹或原始 IMU。所有联系人、位置和事件记录提供清除与保留期限设置。

#### 4.5.4 误报、漏报与失效处理

- [ ] `[验证]` 建立按车型、安装位置、安装角度、支架和路面分类的数据集，统计混淆矩阵、误报率、漏报率、检测延迟、取消成功率和联系人送达率；不能用“演示成功一次”作为安全结论。
- [ ] `[验证]` 单独采集发动机/排气、风噪、喇叭、音乐、导航播报、雨水、碎石、减速带和真实受保护碰撞的音频特征，测量麦克风削波、风罩、安装朝向、扬声器回授和音频播放时的可用性；音频证据缺失时算法仍必须安全降级为 IMU/GPS 路径。
- [ ] `[验证]` 覆盖手机锁屏/后台、厂商省电、权限撤销、通知关闭、BLE 断开重连、定位过期、无网、无 SIM、低电量、圆屏重启、IMU 掉线/饱和、支架松脱和手机被摔坏等失效场景。任何关键链路失效都显示“无法保证通知”，不能显示保护已生效。
- [ ] `[验证]` 先做只记录不通知的台架、推车和封闭道路回放，再做测试号码沙盒通知，最后由安全人员授权小范围实车灰度；自动通知上线前必须审查误报骚扰、漏报责任、隐私、短信费用、厂商后台限制和适用法规。
- [ ] `[暂缓]` 自动拨打公共急救号码、直接控制车辆或声称“已确认人员受伤”暂不实现；这些动作需要独立的法律、保险、运营商和安全审查，以及比当前圆屏更高等级的传感器和通信冗余。

#### 4.5.5 OTA 可行性与交付闸门

- 固件 QMI8658 驱动、候选状态机、BLE 协议和圆屏提示原则上可通过现有签名 OTA 更新；Android 前台服务、权限、联系人设置和通知逻辑原则上可通过 App 更新。
- 真实可靠性不能靠 OTA 自动获得：传感器安装、车型标定、手机厂商后台策略、SIM/运营商、网络覆盖、第三方可穿戴或独立通信模块、实车数据、法规和安全审查都标记为 `[验证]` 或 `[外部硬件/无法仅靠 OTA]`。
- [ ] `[验证]` 在完成数据集、混淆矩阵、故障注入、端到端联系人 ACK 和人工取消测试前，路线图保持 `deviceTested=false`，功能仅允许诊断采样和回放，不允许真实联系人自动通知。

## 7. 建议的实际开发顺序

### 阶段 A：1.75C 稳定基线，必须 USB

1. 完成屏幕、触摸、旋转、PMU、电池、音频和 BLE 的实机测试。
2. 修复所有会导致死机、花屏、触摸失灵、无法重连和异常关机的问题。
3. 增加固件版本、板型、协议版本和设备能力查询。
4. 固定一版可靠的 1.75C 基线固件，保存完整镜像、应用镜像和 SHA256。

### 阶段 B：OTA 基础设施，必须 USB 一次

1. 先用 USB 刷入带 BLE OTA 能力的基础固件。
2. Android App 增加固件包读取、manifest 校验、分块传输和进度显示。
3. 实现升级中断、断电、错误包、错误板型和失败回滚测试。
4. OTA 成功后读取设备版本，确认新旧 App 协议兼容。
5. 发布第一版“可 OTA 升级”的稳定基线。

### 阶段 C：后续功能尽量 OTA

1. 先更新显示和交互，不改分区和 Bootloader。
2. 再更新导航算法、地图渲染、天气、音乐和提示策略。
3. 每个版本都保留回滚版本和 USB 救砖镜像。
4. 只有涉及 Bootloader、分区、OTA 机制或严重兼容变化时，才重新 USB 烧录。
